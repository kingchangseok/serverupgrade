# [문서 1] 엔지니어 수정 내용 비교 분석 (Fatal glibc error 대응)

엔지니어는 `Fatal glibc error` (malloc assertion failure) 및 시스템 호출 행 현상을 해결하기 위해 두 가지 전략을 사용했습니다.

## 1. Malloc 상태 체크 비활성화
메모리 오염 감지 시 프로그램을 즉시 중단시키는 설정을 껐습니다.

### 수정 전 (`server_2`)
```c
/* ecams_svr.c */
// 별도의 malloc 제어 설정이 없거나 기본값(환경에 따라 다름) 사용
```

### 수정 후 (`server_1`)
```c
/* ecams_svr.c */
setenv("MALLOCK_CHECK_", "0", 1); // 0: 에러 무시 및 강제 종료 방지
```
> [!NOTE]
> `MALLOCK`은 오타(K 포함)로 인해 실제로는 작동하지 않을 가능성이 높으나, 의도는 메모리 오류로 인한 크래시를 강제로 막으려는 것입니다.

---

## 2. 시스템 함수 우회 (Bypass)
`malloc` 오류가 발생한 상태에서 시스템 함수(`getpwuid` 등)를 호출하면 내부적으로 힙을 점검하다가 행(hang)이 걸리거나 죽습니다. 이를 피하기 위해 해당 함수를 호출하지 않도록 수정했습니다.

### 수정 전 (`server_2`)
```c
/* output.c / decode.c / encode.c */
pw = getpwuid(uid); // 시스템 라이브러리(NSS) 호출 -> 메모리 오염 시 여기서 Hang 발생
gr = getgrgid(gid);
```

### 수정 후 (`server_1`)
```c
/* output.c / decode.c */
// 시스템 함수 호출을 주석 처리하고 직접 파일을 읽음
// pw = getpwuid(uid);
if(get_username_from_file(uid, username, sizeof(username)) == 0) { ... }
```

---

## 3. 엔지니어 수정한 내용의 특징
- **장점**: 당장 프로그램이 죽거나 멈추는 현상을 외견상 해결했습니다.
- **단점**: 
    - **오타**: `MALLOCK_CHECK_` 오타로 인해 실제로 크래시 방지 효과가 없을 수 있습니다.
    - **근본 원인 방치**: 메모리 어딘가가 깨지고 있는 문제는 여전하며, 나중에 더 큰 데이터 오류로 이어질 수 있습니다.
    - **새로운 버그**: 우회 코드를 만드는 과정에서 `decode.c` 등에 세그멘테이션 오류를 유발하는 버그가 새로 추가되었습니다.
